Hexjack Lens · Software assurance

Know what you're deploying.

Lens now has a controlled CI release path that builds native and OCI artifacts from one source revision and generates software-supply-chain evidence alongside them. Final customer release assurance remains a separate delivery gate.

Software Bill of Materials

Controlled release builds generate CycloneDX SBOM evidence for native and OCI artifacts.

Vulnerability assessment

The controlled path runs Go vulnerability checks, dependency and artifact vulnerability assessment, and source secret scanning with blocking policy for required findings.

Immutable identity

The release workflow captures the pushed OCI image by immutable digest rather than relying only on a mutable tag.

Signing

The controlled release path includes keyless OCI signing through the CI identity boundary; customer verification and final release-assurance packaging remain separate acceptance work.

Build provenance

The workflow records controlled build inputs and release metadata so source revision, build process and resulting artifacts can be traced together.

Customer evidence

Permissions, network requirements, known limitations and relevant release evidence can support an organisation's own approval process.

Evidence, not theatre

The aim is not to ask customers to trust a security claim.

It is to give their engineering and security teams useful evidence with which to assess the software themselves. Assurance claims should never exceed the evidence produced for the artifact concerned.

Lifecycle

Useful after release too.

A software inventory remains useful when new vulnerability information appears. The assurance model is designed so released artifacts can be assessed against later findings rather than reconstructing their contents from memory.

Artifact identity also supports controlled replacement and rollback when required.

Software assurance is one part of Secure by Design.
