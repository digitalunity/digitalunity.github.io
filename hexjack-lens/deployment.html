Hexjack Lens · Deployment

Your infrastructure. Your boundary.

Hexjack Lens is a deliberately small Go application designed around an OCI-first deployment model, with native builds as a secondary path. Organisation-specific configuration and credentials remain outside the application artifact while the final supported deployment baseline is completed.

Current engineering stage

Buildable and scanned, not yet presented as a finished deployment product.

The engineering pipeline builds native and OCI development artifacts. The OCI runtime is digest-pinned, includes exact Git and CA package versions, runs as a non-root user and is vulnerability-scanned in CI. The controlled release workflow adds SBOM, signing and provenance, while the supported deployment baseline and customer verification path remain separate V1 work.

OCI-first

OCI is the intended portable artifact contract. Docker, Podman, containerd, Kubernetes and OpenShift are runtime or orchestration choices rather than different Lens product builds.

External secrets

Lens resolves logical credential references at runtime, keeping credential material separate from both the application artifact and non-secret topology.

Native option

The engineering pipeline already builds native Go binaries. The supported native deployment and customer-verification baseline is still being completed.

One application

A portable deployment boundary.

The same Lens source and application boundary feeds OCI and native build paths. Customer-specific values do not require customer-specific application builds.

A container is packaging and runtime isolation, not a security claim by itself. Host, identity, network, secrets and orchestration controls remain part of the deployment security model.

Restricted environments

No mandatory callback is part of the target runtime design.

The deployment architecture is designed so Lens does not need to contact Digital Unity simply to operate. Controlled artifact transfer, internal registries and native artifact import are part of the planned path for environments where direct access to public infrastructure is inappropriate.

Deployment choices

Keep control where it belongs.

Lens can fit customer-managed or managed-installation models while retaining the same fundamental separation between software, customer configuration and credentials. A future hosted service would require additional architecture around tenant isolation, credential custody and service operation rather than silently weakening those boundaries.

Deployment is part of the security architecture.
