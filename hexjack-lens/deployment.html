Hexjack Lens · Deployment

Your infrastructure. Your boundary.

Hexjack Lens is a deliberately small Go application with an implemented OCI-first deployment baseline and supported native builds as a secondary path. Organisation-specific configuration and credentials remain outside the application artifact.

Current engineering stage

The supported V1 deployment baseline is implemented.

The same Lens source revision produces the primary OCI artifact and supported native binaries. The OCI runtime is digest-pinned, uses exact Git and CA package versions, runs as a non-root user, keeps customer topology and credentials external, exposes local health/readiness/version checks and is verified under a read-only root filesystem with explicit writable cache state. PR and release workflows vulnerability-scan the built image.

OCI-first

OCI is the implemented portable artifact contract. Docker, Podman, containerd, Kubernetes and OpenShift consume the same Lens artifact rather than requiring different product builds.

External secrets

Lens resolves logical credential references at runtime, keeping credential material separate from both the application artifact and non-secret topology.

Native option

The controlled pipeline builds supported native Go binaries from the same exact source revision as the OCI artifact, with checksums, vulnerability evidence, signing and provenance.

One application

A portable deployment boundary.

The same Lens source and application boundary feeds OCI and native build paths. Customer-specific values do not require customer-specific application builds.

A container is packaging and runtime isolation, not a security claim by itself. Host, identity, network, secrets and orchestration controls remain part of the deployment security model.

Restricted environments

No mandatory Digital Unity callback is required to start or validate Lens.

CI proves local health, version, readiness and network-plan generation with networking disabled. Lens derives approved remote HTTPS destinations from trusted topology and rejects unconfigured HTTP targets before network I/O, giving operators a concrete plan for customer-controlled firewalls, proxies or equivalent egress policy. Local document sources and Unix analysis providers can require no remote TCP destination at all. Final customer-facing offline verification and assurance packaging remains V1 work.

Deployment choices

Keep control where it belongs.

Lens can fit customer-managed or managed-installation models while retaining the same fundamental separation between software, customer configuration and credentials. A future hosted service would require additional architecture around tenant isolation, credential custody and service operation rather than silently weakening those boundaries.

Deployment is part of the security architecture.
